1. Configuración de Base de Datos y Despliegue en Tiempo Real

Topología de Red (Docker & Volumenes)

La base de datos principal no opera de forma aislada, es el corazón de una red segura basada en puentes físicos:

  • Motor Principal: Imagen oficial timescale/timescaledb:latest-pg15. Expuesto internamente en red aislada bajo el puerto 5432.
  • Extensión PostGIS: Habilitado dinámicamente (`CREATE EXTENSION IF NOT EXISTS postgis`) para resolver consultas poligonales espaciales de trazabilidad Lidar.
  • Volúmenes Físicos: Mapeo directo db_data:/var/lib/postgresql/data garantizando persistencia ante destrucción del contenedor.
  • Provisión en Frío: Sincronización inmutable. 28 scripts nucleares en ./db_scripts inyectados secuencialmente vía /docker-entrypoint-initdb.d/ cubren desde el Schema Init hasta los roles de auditoría multidimensional.

Políticas Operativas (Throughput & HA)

El cluster exige rendimiento predictivo bajo avalanchas de telemetría IoT:

  • Tolerancia de Fallo a nivel App: Las rutinas C++ encapsulan reintentos transaccionales (Connection Pooling asíncrono con LibPQ).
  • Healthchecks Estrictos: Orquestador Docker sondea repetitivamente pg_isready -U sensors -d sensors_db, blindando los micro-servicios. Ningún gateway arranca si la capa DB sucumbe.
  • Concurrencia: Diseño Multi-Tenant forzado a nivel de llave foránea (`tenant_id UUID`). Las consultas siempre filtran por inquilino usando índices b-tree compuestos `CREATE INDEX idx_... (tenant_id, time DESC)`.

5. Arquitectura de Triggers Asíncronos, Alertas (Fan-Out) e Integradores ETL

La maravilla asíncrona arquitectónica reside en los triggers embebidos (PL/pgSQL). Este diagrama de estados transicionales detalla la coreografía desencadenada por una falla, cruzando a través de tablas outbox y ETL syncs.

@startuml
skinparam DefaultFontName "Inter"

title Patrón Arquitectónico Fan-Out (Triggers DB & ETL Outbox)

[*] --> Falla_Capturada

state Falla_Capturada : Insert en `sensor_process_alarm_queue`
state Falla_Capturada {
  [*] -> Trigger_01
  Trigger_01 : **trg_sensor_process_alarm_queue_to_alert()**
  Trigger_01 : Convierte cola volátil en alerta persistente.

  [*] -> Trigger_02
  Trigger_02 : **trg_alerts_after_insert_fanout()**

  Trigger_02 : 2. Cruza con `org_notify_recipient`

Alerta_Creada --> Fan_Out_Engine

Detalle de Funciones Nucleares DB (Triggers Analizados):

  • update_modified_column(): Mantenimiento C.R.U.D. estándar. Actualiza updated_at al instante actual antes de aplicar mutaciones a entidades madre (Projects, Reports).
  • trg_fn_sensor_process_alarm_queue_to_alert(): Limpieza. Una vez evaluada la alerta prioritaria, se limpia la cola rápida y se deposita formalmente como infracción tipificada en alerts preservando Metadata JSONB y Trazabilidad.
  • fn_alarm_enqueue_deliveries() / fn_org_notify_fanout: Loop procedural robusto que itera la matriz de severidades, grupos de operarios y áreas mineras. Es la "central telefónica" de la base de datos capaz de empotrar 50 mensajes de salida por cada 1 insumo del sistema. Garantiza cero acoplamiento (Desacoplo de la transacción primaria IoT).
  • trg_fn_auth_audit_security_after_insert(): Vigilante (Watchdog) Biométrica. Dispara notificaciones instantáneas hacia CISOs y equipos lógicos si hay accesos recurrentes denegados o biometría fallida cruzada contra las alarmas en el esquema org_notify_route (Categoría 'security').
