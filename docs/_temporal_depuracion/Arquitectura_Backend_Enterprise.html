2. Estructura de Componentes, Librerías y Módulos Internos

Carga de Dependencias Base (Includes)

  • <boost/asio> & <boost/beast>: Manejo total de I/O asíncrona, red HTTP y actualización WebSocket (Telemetry Streams).
  • <libpq-fe.h>: Driver nativo en C utilizado para empujar queries SQL masivos contra PostgreSQL en tiempo cero descartando ORMs lentos.
  • <opencv2/opencv.hpp>: OpenCV 4 utilizado para el bufferado binario de imágenes en memoria antes de transferir a los modelos IA y detectar rostros (Haar Cascades Fallback).

Módulos Físicos del Código (.cpp/.hpp)

  • map_geo_intersect.cpp: Implementa boost::geometry. Carga polígonos (GeoJSON) y utiliza un R-Tree computacional para evaluar intercepciones en milisegundos.
  • onnx_cartoon.cpp: Llama dinámicamente a la red local ONNX Runtime para procesar transferencias de estilos neurales in-house (Avatares) sin salir del contenedor.
  • text_spell_service.cpp: Un bus puente que procesa el estado del teclado local del usuario hacia Ollama (LLM) y LanguageTool de forma transaccional.

Operación Concurrente bajo Bloqueos (Mutexes)

Las librerías y estructuras del backend operan sincronizadas. Explicación funcional:

  • gAuthSessionMutex: Aísla los hilos al instante de leer gAuthSessions. Garantiza que la validación masiva JWT de múltiples sensores y usuarios no corrompa los punteros (Segfaults).
  • GlassesEmaState / gGlassesEmaMutex: Mantiene la "histéresis matemática" del Analizador de Gafas (Oclusión del Face Engine MediaPipe). El backend exige mantener el histórico temporal para el usuario activo (Stateless HTTP to Stateful State), para que el score del ojo no fluctúe de forma errática.
  • LibPQ Pooling Nativo: Un framework ORM (Object-Relational Mapping) tradicional saturaría la memoria. Usar LibPQ (C-bindings puros) nos permite construir Strings SQL en bruto directamente en buffers nativos hacia TimescaleDB.
