# ADR-201 — Export nativo completo: XLSX de tablas, PPTX reconstruido desde JSON, índice/marcadores reales en PDF y contraseña opcional

**Status**: implemented, verificado por build real del backend (Docker, `Dockerfile.verify`, CTest 100%) + typecheck completo del frontend (`tsc --noEmit`, 0 errores) + pruebas unitarias directas de cada builder/módulo nuevo del sidecar (Node). Sin verificación E2E en vivo contra Chromium real todavía (pendiente, ver Consecuencias).
**Fecha**: 2026-09-20
**Autores**: Claude (sesión con Luder Armas)
**Ámbito**: reports

## Contexto

El 2026-09-18 (sin ADR propio, código posterior a este registro) se resolvió el export DOCX para que `pdf-export-service/reportDocxBuilder.js` arme el `.docx` directamente desde el modelo JSON del informe (`window.__REPORT_DOCUMENT__`), con un modo `flow` (texto continuo que reflowa, alternativa al `absolute` de [ADR-139](139-exportacion-docx-nativa-cliente.md)) expuesto en la UI como botón "DOCX (fluido)".

El resto de los formatos se había quedado atrás de ese estándar:

- **PPTX** ([ADR-083](083-exportacion-pptx-modo-presentacion-sidecar-hibrido.md)) capturaba cada página completa como una imagen de fondo y solo superponía cuadros de texto nativos para bloques `text` — tablas/imágenes/KPIs quedaban horneados en píxeles, nunca editables.
- **XLSX** no existía como formato de export en absoluto.
- **PDF** ya tenía texto real (Chromium imprime el DOM real vía `page.pdf()`, no rasteriza), pero no tenía marcadores de navegación ni el bloque TOC visible era clickeable en el archivo exportado, y el cifrado con contraseña ([ADR-080](080-marca-de-agua-y-password-pdf.md)) era siempre obligatorio, sin opción de omitirlo para usuarios avanzados.

Pedido explícito: llevar PPTX y XLSX al mismo estándar que DOCX, y cerrar las brechas de navegación/permiso en PDF, soportando además documentos grandes con la misma precisión ya validada en DOCX (checkpoint reanudable por hash de contenido).

## Decisión

**Fase A — Extracción compartida.** Se saca de `reportDocxBuilder.js` todo lo puro/agnóstico de formato a `pdf-export-service/reportSharedHelpers.js`: conversión de unidades (`pxToTwip`/`pxFontToHalfPt`/`pxToPt`/`pxToInch`), color/fuente (`cssColorToHex`/`firstFontFamily`), resolución de spans con estilo por rango (`sanitizeSpans`/`buildStyledSegments`), extracción/numeración de encabezados para el índice (`extractHeadings`/`numberHeadings`/`generateTocData`/`tocSliceForElementId`/`tocRowRectsForElement`), tamaño de papel (`resolvePagePaperSetup`/`paperSizeInches`), y un parser HTML→runs neutro (`parseHtmlToRuns`, con `bold`/`italic`/`underline` en `true`/`undefined` — nunca `false` — para que cada adaptador de formato pueda heredar el estilo base sin apagarlo por accidente). `reportDocxBuilder.js` se reduce a lo específico de la librería `docx` (mapeo a `TextRun`/`Table`/`TableOfContents` nativos). Del lado de `server.js`, las piezas de checkpoint/readiness de captura raster (antes solo usadas por `/render-docx`) se extraen a `rasterCapturePipeline.js`: `RASTER_ELEMENT_TYPES` (los 4 tipos sin representación nativa: `chart`/`sensor_multi_chart`/`cover`/`image`), y un checkpoint por hash de contenido COMPARTIDO entre DOCX y PPTX (mismo directorio `raster_checkpoints/<hash>/` — capturar primero a DOCX y después a PPTX del mismo informe reusa los PNG ya hechos). La orquestación de workers en sí (abrir N Chromium dedicados, particionar por rango de página) se dejó **deliberadamente duplicada** entre `/render-docx` y `/render-pptx` en vez de extraerse a una función común: es el código más frágil/ajustado del sidecar (condiciones de carrera de CDP ya documentadas in-line), y el riesgo de una abstracción compartida mal probada superaba el beneficio de deduplicar ~150 líneas ya estructuralmente casi-idénticas.

**Fase B — PPTX reconstrucción nativa.** `reportPptxBuilder.js` (nuevo) arma cada diapositiva directamente desde el JSON con `pptxgenjs`: texto (runs con estilo real, hipervínculos), tablas (`addTable` nativo, bordes/shading/anchos reales), KPI/sensor (tarjeta con forma + texto), TOC (lista nativa con hipervínculo REAL `hyperlink:{slide:N}` a cada diapositiva — pptxgenjs no tiene un "campo TOC" vivo como Word). Solo los 4 tipos de `RASTER_ELEMENT_TYPES` se insertan como imagen capturada, con el MISMO checkpoint por-elemento que DOCX. `/render-pptx` se reescribió para capturar por elemento (antes: página completa) y llamar al nuevo builder. Efecto colateral encontrado y corregido: `/render-video` (conversión PPTX→MP4 con narración, [ADR-084](084-conversion-pptx-video-narracion-diapositiva.md)) asumía que cada diapositiva del `.pptx` tenía exactamente UNA imagen de fondo (la captura de página completa vieja) — con el rebuild nativo una diapositiva puede tener 0..N imágenes propias. Se agregó `captureSlidePreviewsForVideo` (solo quiere para `layoutMode:'presentation'`, único modo desde el que la UI permite exportar video) que genera un frame rasterizado por diapositiva en un directorio separado (`SLIDE_PREVIEW_ROOT/<jobId>/`), y `/render-video` ahora lee de ahí en vez de extraer imágenes del `.pptx`. El mecanismo de overlay DOM ya obsoleto (`pptxOverlayMapping.ts`, atributos `data-pptx-overlay`/`data-pptx-meta` en `ReadOnlyViewer.tsx`, query param `pptxOverlay=1`) se retiró por completo. `adm-zip` (usado solo para leer el `.pptx` en `/render-video`) se eliminó como dependencia.

**Fase C — XLSX (nuevo).** Alcance confirmado explícitamente con el usuario: exporta ÚNICAMENTE los bloques `table` ya insertados en el informe (las mismas tablas que ADR-139/172 ya exportan a Word) — `reportXlsxBuilder.js` (nuevo, `exceljs`) genera una hoja real por tabla (celdas con formato numérico real cuando el contenido es puramente numérico, rich text con estilo por-run, hipervínculos reales cuando la celda entera es un link, bordes/shading replicando `props`) más una hoja "Índice" primera con hipervínculos internos reales (`#'Hoja'!A1`) a cada tabla — el equivalente Excel del campo TOC de Word. Nueva ruta `/render-xlsx` (sin fase de captura raster: XLSX nunca toca `chart`/`image`/`cover`). Nuevo formato en el backend: `runXlsxExportJob` (`report_export_jobs.cpp`), ruta `POST /api/reports/{id}/export/xlsx` (mismo permiso `informes.view` que docx/pptx/pdf, sin código dedicado), migración `db_scripts/111` (agrega `'xlsx'` al `CHECK` de `export_format`). Frontend: botón "XLSX" en la cinta, `handleExportXlsx`/`createXlsxExportJob` mirroring el patrón job+poll+descarga de PPTX/DOCX.

**Fase D — PDF: índice real y contraseña opcional.** `pdfPostProcess.js` (nuevo) post-procesa el `PDFDocument` de pdf-lib YA fusionado (todas las páginas de todos los workers, antes de `encryptPdf`): `addPdfOutline` construye un árbol de marcadores REAL (panel de navegación de Acrobat/Chrome) a mano con la API de bajo nivel de pdf-lib (`context.nextRef`/`obj`/`assign`, encadenando `/First`/`/Last`/`/Next`/`/Prev`/`/Parent` por nivel de anidamiento, cada ítem con `/Dest` apuntando a la página ya fusionada; `pdf-lib` no expone una API de alto nivel para esto, a diferencia de `docx::TableOfContents`) — verificado con una prueba de round-trip (guardar, recargar, navegar el árbol) contra un informe simulado de 3 páginas con jerarquía h1/h2 real. `addTocLinkAnnotations` agrega una anotación `/Subtype /Link` con acción `/GoTo` real sobre cada fila VISIBLE del bloque `toc`, usando la MISMA matemática de layout que ya usa `reportDocxBuilder.js`/pantalla (`tocRowRectsForElement`) — deliberadamente NO vía anchors HTML (`<a href="#pagina-N">`), porque cada worker de `/render-pdf` renderiza su propio rango de páginas como PDF aislado antes del merge, así que un ancla del DOM no sobreviviría ese corte; el enlace se resuelve DESPUÉS del merge, contra el índice de página ya fusionado. Ambas funciones son no-op silencioso (con log de advertencia) si el informe no tiene encabezados/TOC, y nunca hacen fallar un export que por lo demás salió bien.

Para la contraseña opcional: nuevo permission code `informes.export_sin_clave` (`db_scripts/112`, sembrado a `admin`+`manager` — perfiles "avanzados") registrado primero en `platform_permissions` y luego en `role_permissions` (patrón real de la tabla, `permission_code` tiene FK a `platform_permissions.code`). `POST /export/pdf` acepta `{"unprotected": true}` en el body; si viene `true`, se exige el permission code ANTES de tocar el sidecar (403 si no lo tiene) — nunca se pasa un `true` de un rol sin permiso como si fuera `false` en silencio. `runPdfExportJob` gana un parámetro `bool unprotected = false` que se traduce a `{"encrypt": !unprotected}` en el body al sidecar (antes: `{"encrypt": true}` hardcodeado). Frontend: botón "PDF (sin contraseña)" en la cinta, visible solo cuando `hasPermission('informes.export_sin_clave')` es verdadero (mismo patrón que gatea otras acciones en `ReportsAdminModal.tsx`).

## Consecuencias

- El sidecar gana 3 archivos nuevos (`reportSharedHelpers.js`, `rasterCapturePipeline.js`, más `reportPptxBuilder.js`/`reportXlsxBuilder.js`/`pdfPostProcess.js`) que comparten código real con `reportDocxBuilder.js` en vez de triplicarlo — un cambio futuro a la resolución de spans/TOC se hace en un solo lugar para los 4 formatos.
- PPTX gana fidelidad/editabilidad real (texto/tablas/KPIs seleccionables en PowerPoint, no una imagen) al costo de una captura por-elemento más cara que la vieja captura de página completa (mismo trade-off ya aceptado para DOCX en ADR-139).
- XLSX es un formato nuevo con alcance intencionalmente angosto (solo tablas) — no reemplaza ni compite con el motor de tablas/fórmulas de [ADR-172](172-motor-tablas-excel-formulas-formato-condicional.md) (ese vive en el editor; esto es solo export).
- El árbol de marcadores de PDF se genera COLAPSADO por defecto (`/Count` negativo en cada rama) para no abrumar el panel de navegación en informes con cientos de encabezados — el usuario expande manualmente.
- Un nuevo permission code (`informes.export_sin_clave`) amplía la matriz RBAC — cualquier tenant puede reasignarlo a otros roles vía la pantalla de permisos existente, sin código nuevo.
- **Pendiente real, no cerrado en esta pasada**: verificación E2E contra Chromium real (los 4 exports — DOCX/PPTX/XLSX/PDF — abiertos en Word/Excel/PowerPoint/Acrobat reales, con un informe grande de verdad) y prueba en vivo del flujo de permiso 403 con una sesión de rol no-admin real. La verificación hecha esta pasada fue: build C++ real (Docker, CTest 100%), typecheck completo del frontend (0 errores), y pruebas unitarias directas de cada función nueva del sidecar contra documentos JSON sintéticos (incluye round-trip real de los PDF de prueba con pdf-lib). Se recomienda cerrar la verificación E2E como siguiente paso antes de considerar esto `implemented` sin reservas.

## Alternativas descartadas

- **Reusar la captura de página completa para PPTX** (mejora incremental del overlay en vez de reconstrucción nativa): descartada explícitamente por el usuario — la reconstrucción nativa completa era el pedido.
- **`pptx.addSection()` nativo de PowerPoint como índice** (agrupar diapositivas en secciones visibles en el Organizador de diapositivas): evaluado y descartado por esta pasada — su semántica de asignación (`addSlide({sectionTitle})` vs. auto-asignación a la última sección creada) no estaba lo bastante probada como para arriesgar reordenar/reagrupar diapositivas por accidente; el índice clickeable (`hyperlink:{slide:N}`) ya cubre el requisito real de navegación.
- **Anchors HTML (`<a href="#pagina-N">`) para el TOC clickeable del PDF**: descartada — no sobrevive el corte de cada worker renderizando su propio rango de páginas como PDF aislado antes del merge (ver Decisión, Fase D).
- **XLSX con hoja de resumen KPI/sensor o volcado de telemetría cruda**: descartado tras aclaración explícita del usuario — el alcance real pedido era exportar las tablas ya insertadas, nada más.
