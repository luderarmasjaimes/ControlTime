# Cotas superiores deliberadas: sin ellas, un rebuild sin cache trae la
# ultima version major de cada libreria (visto en la practica: mediapipe
# salto de 0.10.x a 1.0.0, opencv-python-headless de 4.x a 5.0.0,
# insightface de 0.7.x a 1.0.1 -- todas con cambios de API/umbrales que
# rompieron la deteccion/tracking facial en produccion sin ningun cambio
# de codigo). Mantener en la misma linea major.minor que se probo al
# escribir eye_analyzer.py / face_embedding_insight.py; subir de linea
# es una decision explicita, no un efecto colateral de un rebuild.
#
# Evaluacion 2026-08-07 (ver PyPI/GitHub release notes de cada libreria),
# migracion a NumPy 2.x aplicada el mismo dia:
# - numpy>=2: onnxruntime>=1.16 y opencv-python-headless>=4.12 ya lo
#   requieren. El bloqueador real era insightface 0.7.3 (abr-2023), que usa
#   np.int (alias eliminado en NumPy 1.24+) en
#   insightface/app/face_analysis.py:84 -- bug confirmado y ya corregido en
#   la rama master del proyecto pero nunca publicado a PyPI
#   (github.com/deepinsight/insightface/issues/2404). Se resuelve con un
#   shim que restaura np.int/np.float/np.bool/np.object/np.str antes de
#   importar insightface, ver face_embedding_insight.py.
# - opencv-python-headless: >=4.14 fuerza la ultima release de la linea 4.x
#   estable (4.14.0.94, jul-2026); <5 sigue vetando la 5.0.0 (jun-2026,
#   primera version mayor desde 2018, demasiado nueva/sin probar con
#   mediapipe/insightface pese a que su propia doc dice "casi sin cambios
#   de API" para Python).
# - onnxruntime: onnxruntime>=1.24 ya exige Python >=3.11 (este contenedor
#   corre 3.10, ver Dockerfile.ai) -- 1.23.2 (oct-2025) es la ultima con
#   wheel cp310, asi que <1.24 sigue siendo el tope aunque numpy ya no lo
#   fuerce.
# - mediapipe 1.0.0 (jul-2026, ~11 dias de antiguedad al evaluar) y
#   insightface 1.0.x (may-2026) se mantienen sin tocar: ambos son
#   releases mayores muy recientes con cambios de API/paquete documentados
#   (namespacing en mediapipe Tasks API; extras opcionales en insightface)
#   sin ciclo de prueba todavia -- la migracion a NumPy 2.x es ortogonal a
#   esa decision.
# Corrección 2026-08-13: opencv-python-headless>=4.12 exige numpy>=2 (ver
# requires_dist real en PyPI, distinto de lo que decia el comentario de
# arriba) -- incompatible en tiempo de ejecucion con tensorflow<2.16
# (AttributeError: _ARRAY_API not found / crash de mediapipe->tensorflow al
# importar, confirmado en el contenedor). Fijado a 4.11.0.86 (ene-2025,
# ultima release 4.x que NO exige numpy>=2 para Python 3.10) hasta que
# tensorflow suba de linea (ver nota de Keras 3 mas abajo). Las tres
# variantes de opencv deben ir a la MISMA version exacta, no solo el mismo
# tope <5 (ver comentarios originales sobre la carrera de instalacion).
opencv-python-headless==4.11.0.86
# opencv-contrib-python: dependencia transitiva (albumentations/insightface),
# NO declarada aqui arriba. Comparte el paquete "cv2" con
# opencv-python-headless -- quien se instale despues sobrescribe los
# archivos del otro en site-packages. Sin este pin, trajo 5.0.0.93 y gano
# la carrera, dejando cv2.__version__ en 5.0 pese al <5 de la linea de
# arriba. Se fija a la misma version exacta que opencv-python-headless.
opencv-contrib-python==4.11.0.86
# Mismo problema, causado ahora por deepface: arrastra mtcnn/retina-face
# (detectores que este adaptador no usa -- se fuerza detector_backend="yunet"
# en deepface_silentface_adapter.py) que exigen "opencv-python>=4.5.5.64" SIN
# tope superior. Verificado con `pip install --dry-run`: sin este pin, resolvía
# opencv_python-5.0.0.93 (mismo paquete "cv2" que opencv-python-headless de
# arriba) reintroduciendo la carrera de instalación que ya rompió la línea de
# opencv-contrib-python.
opencv-python==4.11.0.86
mediapipe>=0.10.9,<0.11
flask

numpy>=1.24,<2

# Proveedor biométrico primario: DeepFace (Facenet512) + Silent-Face-Anti-
# Spoofing (MiniFASNet). Reemplaza a SeetaFace6 como proveedor local por
# defecto -- ver ai_engine/deepface_silentface_adapter.py.
#
# torch/torchvision YA NO viven acá (Opción C, ADR-141 actualización
# 2026-09-03): Silent-Face-Anti-Spoofing se movió a un servicio propio,
# silentface_engine/ (aislado de TensorFlow por el mismo conflicto real de
# cuDNN documentado en el ADR -- torch exige cuDNN major 9, TensorFlow
# major 8, irreconciliable). ai_engine/deepface_silentface_adapter.py ahora
# le habla por HTTP (silentface_client.py). El paso final de reinstalación
# forzada de nvidia-nccl-cu12 que vivía en Dockerfile.ai también se retiró:
# existía solo para el choque de archivo entre el NCCL de torch y el de
# TensorFlow, que ya no compiten en este proceso.
#
# tensorflow[and-cuda]: DeepFace usa tf.keras para construir/cargar Facenet512.
# El extra "and-cuda" trae las librerías CUDA/cuDNN como dependencias pip
# (mismo razonamiento que torch arriba). Se fija <2.16 para evitar el cambio
# de Keras 3 como backend por defecto (TF 2.16+), no probado todavía con la
# versión de DeepFace fijada aquí.
# Version EXACTA (no rango) 2026-08-20: con ">=2.14,<2.16" pip backtrackeaba
# entre 2.15.1/2.15.0.post1/2.15.0 buscando una compatible con
# torch==2.11.0+cu128 + numpy<2, re-descargando el wheel completo (475MB)
# en cada intento fallido -- costó >15 min extra en un build. 2.15.1 es la
# que finalmente resuelve sin conflicto (confirmada en ese build).
tensorflow[and-cuda]==2.15.1
deepface>=0.0.85,<0.1
